# Windows Product Capability Matrix

This is the current inventory and public-claim boundary for Boundless. The target is a polished Windows alternative to Mouse Without Borders, beginning with a two-PC public beta and qualifying four computers total separately. It is not a claim that the current 5.0.16 release or hardening candidate is ready for public promotion.

Microsoft's reference product supports up to four computers, keyboard/mouse sharing, clipboard/file workflows, layout, reconnect, and optional service behavior. Its own file workflows have documented restrictions. Matching every optional setting is not a prerequisite for a useful Boundless release; incomplete or unsupported behavior must be visible. [Microsoft Learn, reviewed 2026-09-04](https://learn.microsoft.com/en-us/windows/powertoys/mouse-without-borders)

## Reading Status And Evidence

- **partial:** useful implementation exists, but the user workflow, supported environment, or current acceptance evidence is incomplete.
- **hardening:** the capability is being changed in the current candidate; source and local tests must be qualified against its specific runtime claim.
- **deferred:** outside the current train; no public claim is made.
- **unsupported:** no supported product path; hide or disable any associated affordance.
- **validated:** the exact stated user workflow and environment have current release evidence. No row is promoted to this state by this documentation update.

The evidence column separates historical observations, implementation/local checks, and missing proof. The [launch ledger](../release/launch-ledger.md) retains exact older observations. Current local/source evidence does not silently refresh those runs.

The table's nine-column shape is consumed by `Get-ParityReleaseBlockers` in the release-readiness script: capability, status, evidence, and blocker remain in columns 1, 4, 8, and 9. A `yes` blocker requires matching evidence before that capability is publicly promised, or an explicit release-scope deferral with the claim removed. This snapshot alone is not a passing gate.

## Compatibility And Promotion

The peer-approved test work changes the wire contract to 4.5; 4.4 peers are incompatible and both PCs need compatible builds. The manifests remaining at 5.0.16 during development must not obscure that protocol difference. Configuration migration and rollback constraints belong in the [network architecture](../architecture/network-v1.md) and [migration guide](../user/migration.md).

Schema 6 deliberately removes persisted live observations, including connected/last-seen state, while migrating durable schema-5 configuration/trust data. Rollback requires a private pre-upgrade state backup and compatible old peers. Do not treat an older binary reading the new state as a supported rollback plan.

Before promotion, record the commit/build identity, actual running artifacts, Windows/session/topology context, command or physical scenario, result, and retained evidence for each promised row. Record unsupported cases and deferrals in user-facing documentation. [Release readiness](../release/release-readiness.md) defines gate mechanics; [the scorecard](../performance/product-scorecard.md) defines product interpretation.

The [old matrix](../history/2026-09-04/parity/mouse-without-borders.md) and milestone pages are historical snapshots. They do not add hidden release requirements or override this matrix.
